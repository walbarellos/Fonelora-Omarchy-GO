## Finding F-006 — Canal RPC único: `IRpcHandler.SendRpc`

Todo RPC do jogo passa por um único gargalo:

```
Niantic.Holoholo.Rpc.IRpcHandler (TypeDefIndex 2899)
  IRpcPromise<OutProtoT> SendRpc<InProtoT,OutProtoT>(
      int method, InProtoT inProto,
      int rpcRetryDelayMs = 0, int rpcTimeoutMs = 0, bool beTenacious = false)
```

Implementação: `RpcHandler : MonoBehaviour, IRpcHandler` (TypeDefIndex 2904).
Encaminha para `Niantic.Platform.Ditto.Rpc.IRpcManager` (injetado, campo `dbin @ 0x38`).

**Consequência para o bot:** não precisamos simular UI. Basta construir o proto de
entrada e invocar `SendRpc(method, proto)` — exatamente o que o cliente legítimo faz.
O mesmo resultado seria obtido por toques reais, só que sem a latência de render.

## Finding F-010 — Invocar SendRpc genérico + ler resposta SEM delegate

Dois obstáculos de il2cpp e suas soluções (extraídos de `il2cpp-functions.h` /
`il2cpp-types.h`):

**1. SendRpc é genérico, mas referências compartilham o blob nativo.**
`RpcHandlerExt.Send<InProtoT,OutProtoT>` colapsa para UMA instância nativa
compartilhada (todos argumentos são tipos de referência):
```
0x05F71990  RpcHandlerExt_Send_1(
    IRpcHandler* rpcHandler, Method__Enum method, Object* inProto, MethodInfo* method)
    -> IRpcPromise_1_System_Object_*
0x05F704C4  RpcHandler_SendRpc(
    RpcHandler*, int32_t method, Object* inProto,
    int32_t rpcRetryDelayMs, int32_t rpcTimeoutMs, bool beTenacious, MethodInfo*)
    -> IRpcPromise_1_System_Object_*
```
`MethodInfo*` (globals `IRpcHandler_SendRpc_1..6__MethodInfo`, `RpcHandlerExt_Send_5..10__MethodInfo`)
carrega o contexto genérico real. Basta pinar o `MethodInfo*` certo por par
(InProto,OutProto) — o código nativo é o mesmo.

**2. Resultado lido por poll, sem criar delegate.**
`IRpcPromise<Out>` deriva de `Promise<T>` (TypeDefIndex 45871) que guarda o
resultado em campo privado:
```
struct Promise_1_System_Object_ {   // offsets via il2cpp_field_get_offset em runtime
    klass; monitor; threadCheckerToken;
    whenFuncs; thenFuncs; thenPayloadFuncs; errorFuncs; finallyFuncs;
    bool completeCalled;   // <- poll
    bool errorCalled;
    Object* completedValue; // <- OutProto quando completeCalled==true
    String* errorValue;
}
```
Fluxo por ação:
1. `il2cpp_object_new(ProtoClass)` + `il2cpp_field_set_value` nos campos de entrada.
2. `Send_1(rpcHandler, Method.<id>, proto, methodInfoGenerico)` → `IRpcPromise`.
3. Poll `get_Completed()` (ou campo `completeCalled`) com间隔 humano (já que
   humanizamos o timing de qualquer forma).
4. Quando completo: `il2cpp_field_get_value_object(completedValue)` → `OutProto`;
   `il2cpp_field_get_value` nos campos de resultado (Status, Result, etc.).

Sem `Then(Action<T>)`, sem `Marshal.GetFunctionPointerForDelegate`, sem delegate
managed — o ponto que costuma inviabilizar hooks in-process via JNI.

Caveat: instâncias genéricas compartilhadas significam que `completedValue` é
tipado como `System.Object` no layout; o objeto real é o `OutProto` concreto e
seus campos são lidos pelo `Il2CppClass*` correto.

## Path (WI-007/008)

`libfonescout.so` (arm64, sem root, carregado pelo plugin via System.load):
1. `il2cpp_domain_get` + assemblies → achar image do jogo (`Assembly-CSharp` /
   `Holoholo.Rpc`).
2. Cache de `MethodInfo*` por (namespace, class, method, argc) — resolvido uma vez.
3. `resolve<T>` via `ProjectContext.Instance.Container.Resolve(Type)`.
4. Por ação: `il2cpp_object_new(proto)` → set fields → `SendRpc(id, proto)` →
   aguarda `IRpcPromise` (ou lê resultado síncrono via `IRpcManager`).
5. Inventario via `IItemBag.GetItemCount` (não via proto).

Cada ação exposta ao plugin como novo `BaseRequest` (WI-008) registrada por
`addExtraFunc`, mesmo padrão das 7 ações de localização já existentes.
